# حوكمة إصدارات السياسة ومحاكاة الأثر

## العيب الذي تعالجه هذه الخطوة

قبل M4.06 كانت السياسة ملف YAML: من يملك حق الكتابة على القرص يستطيع تغيير قرار
الدولة مباشرةً. لم يكن هناك اعتماد مستقل، ولا توقيع يربط المعتمد بمادة التعديل،
ولا سجل تغيّرات، ولا تراجع قابل للمراجعة. ذلك عيب في السلطة لا نقص في تجربة
التطوير؛ فسياسة السماح والمنع جزء من القرار السيادي.

تضيف M4.06 مصرف إصدارات في PostgreSQL، وتضيف M4.08 محاكاة تقيس أثر مقترح على
قرارات سابقة قبل أن يعتمد. لا يحل هذا محل مراجعة بشرية، ولا يجعل ملف YAML نفسه
غير قابل للتعديل؛ النسخة التي يقرأها تكامل الحوكمة هي فقط النسخة النافذة
الموقعة في المصرف فوق قاعدة بيانات الملفات.

## دورة حياة نسخة السياسة

1. يرسل المقترح وثيقة سياسة واحدة وسبب التغيير واسم المقترح إلى
   `propose({ policy, reason, proposedBy })`.
2. يخزن المصرف نسخة غير نافذة برقم تالٍ خاص بمعرف السياسة. لا يصح أن تجعلها
   المسودة نافذة من داخل الوثيقة؛ المصرف يفرض `active = false`.
3. يوقّع المعتمد مادة `policyApprovalPayload(...)` بالمفتاح الذي يتحقق منه
   `signer` (تتوافق `KingIdentity` مباشرةً).
4. يستدعي المعتمد
   `approve({ policyId, version, approvedBy, signature })`. تتحقق الوحدة من
   التوقيع على بصمة الوثيقة، ثم تبطل النسخة النافذة السابقة وتفعّل الجديدة في
   معاملة PostgreSQL واحدة.
5. يبني المركّب `await store.bundleWithOverrides(loadPolicyBundle())` ويمرر
   الناتج إلى `new PolicyDecisionPoint({ bundle })`. النسخ النافذة في القاعدة
   تستبدل سياسة الملف ذات المعرف نفسه؛ وتبقى بقية الكتالوج والأدوار والعتبات من
   ملفات التهيئة المقروءة والمتحقق منها.

لا توجد دالة تنشيط قصيرة تتجاوز الاعتماد: `activate(...)` ترفض دائماً بالرمز
`POLICY_CHANGE_UNAPPROVED`.

## قيود قاعدة البيانات

الهجرة `0003_policy_governance` تنشئ:

- `state.policy_versions`: معرّف السياسة، رقم النسخة، وثيقة `jsonb`، سبب
  التغيير، المقترح، المعتمد، التوقيع، حالة النفاذ، ووقت الإنشاء.
- قيد `policy_versions_active_needs_approval`: يمنع النسخة النافذة بلا معتمد
  وبلا توقيع، حتى لو كتب عميل SQL خارج JavaScript.
- قيد فريد على `(policy_id, version)` وفهرس فريد جزئي
  `policy_versions_one_active_per_policy_idx`: يمنع بقاء نسختين نافذتين لسياسة
  واحدة.
- `state.policy_decisions`: الفاعل ودوره وحالته ونوعه ونطاقه، والفعل والمورد
  والسياق، والنتيجة والرمز ومرجع السياسة والنسخة والوقت. تحفظ هذه الحقول لأن
  المحاكي لا يستطيع إعادة تقييم طلب سابق من معرّف فاعل مجرد.

التراجع عن هجرة 0003 يسقط هذين الجدولين فقط، ويفقد سجلاتهما. هذا **حدٌّ معلن**:
تراجع المخطط ليس استعادة للتاريخ؛ تؤخذ نسخة احتياطية قبل تراجع قاعدة استعملت
فعلاً.

## التراجع التشغيلي

التراجع لا يعيد كتابة صف تاريخي. يستدعي المعتمد:

```js
const signature = king.sign(
  policyRollbackPayload({
    policyId: 'pol:read-registry-authorized-roles',
    toVersion: 1,
    policy: historical.policy,
    approvedBy: king.id,
    reason: 'سبب التراجع المراجع',
  }),
);

await store.rollback({
  policyId: 'pol:read-registry-authorized-roles',
  toVersion: 1,
  approvedBy: king.id,
  signature,
  reason: 'سبب التراجع المراجع',
});
```

ينشئ المصرف حدث نسخة جديداً يحمل مادة النسخة المستهدفة ثم ينشطه ذرّياً. لذلك
يبقى سبب الاقتراح والتوقيع القديمان في الصف القديم، ويظهر سبب التراجع وتوقيعه
كحدث مستقل في `history(policyId)`.

## محاكي الأثر

`simulatePolicyChange({ recorded, currentBundle, proposedBundle })` يعيد:

- العدد الكلي للقرارات المقيسة؛
- عدد التحولات من سماح إلى منع؛
- عدد التحولات من منع إلى سماح؛
- عدد القرارات التي لم يتغير فيها السماح أو المنع؛
- حتى عشرين مثالاً مسمّى بالفاعل والفعل والمورد والرمز قبل وبعد.

لقراءة القرارات المخزنة استخدم:

```js
const recorded = await readRecordedPolicyDecisions(pool);
const report = simulatePolicyChange({ recorded, currentBundle, proposedBundle });
```

ولتسجيل قرارات نقطة التفويض، يمرر المركّب
`createPolicyDecisionSink({ pool })` بوصفه `decisionSink` إلى
`EnforcementPoint`. لا ينفذ المحاكي أي `INSERT` أو `UPDATE`، ولا يفعّل نسخة
ولا يخصم حصة.

### أداة سطر الأوامر

```sh
node scripts/policy-simulate.mjs --proposal proposal.yaml
node scripts/policy-simulate.mjs --proposal proposal.yaml --decisions decisions.jsonl
```

الأمر الأول يقرأ `state.policy_decisions` من `DATABASE_URL`. الأمر الثاني يعمل
بلا قاعدة ويقرأ JSONL. يقبل المقترح واحداً من الأشكال التالية:

```yaml
policy:
  id: pol:example
  # بقية حقول PolicyRecord
```

أو سياسة مفردة في جذر YAML، أو `policies:` لمجموعة استبدالات. يحتوي كل سطر
JSONL إما سجلاً بشكل أعمدة `state.policy_decisions`، أو:

```json
{
  "request": {
    "actor": { "id": "agent:x", "role": "role:operator", "state": "active" },
    "action": "read-registry",
    "resource": { "type": "registry", "id": "agents" }
  },
  "allowed": true,
  "code": "POLICY_ALLOW"
}
```

ترفض الأداة غياب `--proposal`، وملف قرارات فارغاً، وغياب كل من `--decisions`
و`DATABASE_URL`؛ لا تطبع تقريراً صامتاً بلا بيانات مقيسة.

## الحدود المعلنة

- يتحقق التوقيع من المفتاح الذي يقدمه `signer`، لكنه لا يربط بعد اسم
  `approvedBy` بسجل أدوار أو تفويض مفاتيح. هذا الربط لم ينفذ في M4.06.
- `bundleWithOverrides` لا يغير ملفات YAML ولا يبدل الأفعال أو الأدوار أو
  العتبات؛ يتجاوز فقط سجلات السياسات النافذة. تعديل الكتالوج نفسه خارج نطاق هذه
  الخطوة.
- يقيس المحاكي القرارات المسجلة فقط. قرار لم يمر عبر `decisionSink` لا يدخل
  التقرير، ولا يجوز قراءة عدم ظهوره دليلاً على عدم تأثره.
- يعيد المحاكي محرك السياسة، لا حصصاً متغيرة ولا حالة الإيقاف الشامل ولا تحقق
  أمر ملكي خارجي. التقرير دليل أثر للسياسة وحدها، لا وعد نتيجة تشغيل كاملة.
