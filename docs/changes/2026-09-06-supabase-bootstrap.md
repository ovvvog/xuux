# الدفعة الثانية — تهيئة قاعدة Supabase التجريبية

## النطاق

رُبط المشروع مؤقتاً بمشروع Supabase التجريبي ذي المعرّف `uhmgnusfihfkdnrdskje` باستخدام Supabase CLI وAccess Token خارج ملفات المشروع. لم تُحفظ كلمة مرور PostgreSQL أو Access Token أو مفاتيح Supabase في Git أو ملفات الإعداد المتتبعة.

## ما نُفّذ على قاعدة البيانات

لأن اتصال PostgreSQL المباشر من بيئة التنفيذ لم يملك مسار IPv6 متاحاً، استُخدم مسار Supabase Management API عبر `supabase db query --linked`. جُمعت ملفات الترحيلات المحلية وعددها 18 مع دفتر `public.schema_migrations` وبصمات SHA-256، ثم أُرسلت في معاملة واحدة مع قفل استشاري. لم يُجرَ أي تعديل عشوائي أو حذف للبيانات.

| الفحص | النتيجة |
|---|---:|
| الترحيلات المطبقة | 18 من 18 |
| الإصدار الحالي | 18 |
| جداول مخطط `state` | 31 |
| قيود مخطط `state` | 375 |
| فهارس مخطط `state` | 117 تقريباً وفق استعلام `pg_indexes` |
| جدول تتبع الترحيلات | موجود في `public.schema_migrations` |
| بصمات الترحيلات | مسجلة لكل الإصدارات من 1 إلى 18 |
| حالة المشروع البعيدة | `ACTIVE_HEALTHY` وفق قائمة Supabase |

## ما لم يُنفّذ بعد

لم يُشغّل `npm run migrate` مباشرة على PostgreSQL لأن مضيف قاعدة البيانات المباشر يعيد عنوان IPv6 لا يمكن الوصول إليه من بيئة التنفيذ. كما فشل `supabase db dump --linked` بسبب اعتماد أمر النسخ المحلي على Docker، وDocker غير متوفر في هذه البيئة. لذلك لا يُقدّم هذا الدليل ادعاءً بأن تمرين النسخ والاستعادة الكامل قد نجح؛ ما تحقق هو تطبيق ترحيلات ذري عبر Management API والتحقق من المخطط والقيود والفهارس.

قبل تشغيل النسخ والاستعادة الفعليين، يجب توفير Docker أو مسار Pooler/IPv4 قابل للوصول، ثم تشغيل `backup create`, `backup verify`, و`restore` فوق قاعدة تجريبية ثانية، وتسجيل الزمن والنتيجة وعدم الاكتفاء بوجود ملف النسخة.

## أمن التشغيل

استُخدمت الأسرار في متغيرات بيئية مؤقتة فقط. لا يحتوي هذا الملف على Access Token أو كلمة مرور أو مفتاح API. ينبغي تدوير Access Token وكلمة مرور قاعدة البيانات بعد انتهاء جلسة العمل إذا كانت البيئة مشتركة أو غير موثوقة.
