# 4 — كتاب التشغيل: كيف يعمل من يأتي بعدي

**الإصدار:** 1.0.0. **التاريخ:** 2026-08-23.

هذه الوثيقة تُجيب على: **كيف أنفّذ عملي في هذا المشروع بطريقة مقبولة؟** القاعدة الحاكمة تقول «ماذا يجب»، وهذه الوثيقة تقول «كيف».

## 4.1 أول ساعة لك في المشروع

نفّذ هذه الخطوات بالترتيب، ولا تكتب سطراً واحداً قبل إتمامها:

1. اقرأ [`../../GOVERNANCE_RULE.md`](../../GOVERNANCE_RULE.md) كاملاً. هي ملزمة لك.
2. اقرأ [`01-project-definition.md`](01-project-definition.md) لتعرف ما تبنيه.
3. اقرأ [`02-baseline-audit.md`](02-baseline-audit.md) لتعرف ما هو حقيقي وما هو وهم.
4. افتح [`03-roadmap-to-100.md`](03-roadmap-to-100.md) وحدّد **أول خطوة غير منجزة** في **أول مسار غير مغلق**. هذه خطوتك، لا غيرها.
5. اقرأ آخر عشر مُدخلات في [`05-work-log.md`](05-work-log.md) لتعرف ما جرى قبلك.
6. شغّل النظام محلياً وأثبت لنفسك أنه يعمل قبل تغييره:
   ```bash
   node --version              # يجب أن يكون 20.x
   node --test tests/*/*.test.mjs   # يجب أن ينجح (27 اختباراً كخط أساس)
   ```
7. لا تبدأ عملاً قبل أن تعلن نيّتك: غيّر حالة خطوتك في الخارطة إلى `🟨` مع اسمك.

## 4.2 دورة العمل على أي خطوة

```
اقرأ الخطوة → تحقّق من شرطها المسبق → أعلن 🟨 → اكتب الاختبار أولاً حيث أمكن
   → نفّذ → شغّل npm run validate → اجعل معيار القبول مُثبتاً بأمر
   → حدّث الخارطة إلى ✅ → اكتب مُدخلة سجل الأعمال → commit → افتح PR
```

**لا تُغلق خطوة إن:** فشل اختبار، أو لم تستطع إثبات معيار القبول بأمر، أو خرجت عن نطاق الخطوة. في الحالة الثالثة، أضف خطوة جديدة بدل توسيع القائمة.

## 4.3 القواعد الهندسية

### اللغة والبنية
- TypeScript صارم (`strict: true`) للخدمات. ESM حصراً. لا `require`.
- `any` ممنوع إلا بتعليق `// وسبب:` يشرح الاضطرار.
- كل حدود وحدة (module) تُصدَّر عبر `index.ts` واحد. لا استيراد من أعماق وحدة أخرى.
- التبعيات الخارجية في **جذر الثقة** ممنوعة إلا بموافقة موثّقة. كل تبعية جديدة تسطر مبرراً في سجل الأعمال.

### الأخطاء والتحقّق
- لا فشل صامت. كل خطأ إما يُعالَج ويُسجَّل، أو يُرمى لأعلى.
- تحقّق من كل مُدخل عند الحدود (‏API، ملف، رسالة). لا تثق ببيانات داخلية بلا مخطَّط.
- لا `catch` فارغ. لا تجاهُل قيمة مُعادة.

### الأمان
- **لا مفاتيح ولا أسرار في المستودع.** أبداً. المخالفة تُفشل البناء (M0.08).
- كل فعل حسّاس يمرّ بنقطة التفويض المركزية (M4.05). لا مسار جانبي.
- كل فعل ذي أثر يُسجَّل في سجل الأحداث بفاعله وسببه ونتيجته.
- عند الشك بين توسيع صلاحية وتقييدها، قيّد وسجّل السبب (المادة 9).

### الاختبار
- كل منطق جديد له اختبار. كل إصلاح خطأ يبدأ باختبار يُظهر الخطأ.
- الاختبارات القائمة (27) خط أساس مقدَّس: من أسقط اختباراً أصلحه أو برّر إسقاطه في سجل الأعمال.
- اختبارات الفشل ليست ترفاً: انقطاع، مهلة، انزياح ساعة، بيانات تالفة، صلاحية ناقصة.

### البيانات مقابل الكود
- **الحكم بيانات، لا كود.** السياسات والقوانين والحصص والأدوار والتقسيم الإداري تُكتب كبيانات ذات مخطَّط، ويقرؤها كود عام.
- كل ملف بيانات له: مخطَّط، مُحقِّق، قارئ في الكود، ومالك. **بيانات بلا قارئ = قالب = ممنوع** (المادة 3).

## 4.4 قالب توثيق الوحدة

مأخوذ من الوثيقة الثانية القائمة (خريطة البناء) بعد تنقيته. يُكتب في رأس كل وحدة أو في `README.md` مجاورها:

```
الغرض:       ما تفعله هذه الوحدة بجملة واحدة دقيقة.
المدخلات:    الأنواع والعقود الفعلية، لا "يحددها العقد لاحقاً".
المخرجات:    الأنواع والأخطاء الممكنة.
التبعيات:    الوحدات التي تعتمد عليها، وسبب كل تبعية.
التشغيل:     الأمر الفعلي لتشغيلها أو استدعائها.
الاختبار:    مسار ملف الاختبار وأمر تشغيله.
الصلاحيات:   ما تحتاجه من تفويض، وهل تمرّ ببوابة التاج.
المالك:      المسؤول عن صحتها.
```

عبارات مثل «يحددها عقد المجال قبل التنفيذ» و«هيكل تأسيسي؛ لا يُفعل قبل اختبارات القبول» **ممنوعة**؛ هي بصمة القوالب القديمة.

## 4.5 مراجعة الأعمال (PR)

كل PR يجب أن يحتوي:

- [ ] معرّف الخطوة من الخارطة في العنوان: `feat(crown): M2.07 منع إعادة إرسال دائم`
- [ ] نجاح CI كاملاً (‏`lint`, `typecheck`, `test`, فحص الأسرار، حاجز القوالب)
- [ ] الأمر الذي يُثبت معيار القبول، ونتيجته، في وصف الـ PR
- [ ] تحديث حالة الخطوة في الخارطة
- [ ] مُدخلة في سجل الأعمال
- [ ] لا ملفات قالبية جديدة، ولا أسرار، ولا تبعية غير مبرَّرة

**يُرفض الـ PR فوراً إذا:** خالف بوابة، أو أعلن إنجازاً بلا دليل، أو أضاف قوالب، أو مسّ `src/` بلا اختبار ولا تبرير.

## 4.6 سجلات القرارات المعمارية

كل قرار معماري ذو أثر (اختيار قاعدة بيانات، نموذج اتساق، تقنية عزل، حدود وحدة) يُكتب في `docs/decisions/NNNN-<عنوان>.md` بهذا الشكل:

```markdown
# NNNN — <القرار>
- **الحالة:** مقترح | معتمد | مستبدل بـ NNNN
- **التاريخ:** YYYY-MM-DD
- **السياق:** المشكلة والقيود
- **القرار:** ما اختير بالضبط
- **البدائل المرفوضة:** وسبب رفض كل بديل
- **الأثر:** ما يتغيّر، وما يصبح أصعب
- **معيار إعادة النظر:** الشرط الذي يوجب مراجعة هذا القرار
```

القرارات المعروفة سلفاً والتي تحتاج سجلاً في M1–M3: تحويل الشجرة إلى بيانات، اختيار PostgreSQL، توحيد TypeScript، تقنية عزل التنفيذ.

## 4.9 قائمة فحص إغلاق أي بوابة

قبل إعلان بوابة G# مغلقة:

- [ ] كل خطوات المسار `✅` أو `⏸️` بسبب مكتوب — صفر `⬜` وصفر `🟨`
- [ ] معيار قبول كل خطوة مُثبت بأمر قابل للتشغيل، لا برأي
- [ ] CI أخضر على `main`
- [ ] الوثائق محدَّثة: الخارطة، سجل الأعمال، `PROJECT_STATUS.md`، جدولة النسبة في 02 §2.9

- [ ] مراجعة مستقلة من غير من نفّذ المسار
