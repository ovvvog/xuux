# `LIVE-39` — تحليلُ عمى اختبارِ طفرةِ `fsync` المجلّدِ وتصميمُ العلاجِ (‏`WL-503`)

> **وثيقةُ تحليلٍ وتصميمٍ لا قرار.** لا تُغلِقُ `LIVE-39`، ولا تغيّرُ حالةَ دَينٍ، ولا تمسُّ كودَ الإنتاجِ ولا
> أداةَ القياسِ ولا ضماناتِ الدوام. تُكمِلُ [حزمةَ القرارِ](LIVE-39-decision-package.md) §5.3 بتفسيرٍ مقيسٍ
> لسببِ العمى، وتقترحُ علاجاً مُقسَّماً إلى ما يملكُه المنفِّذُ وما يُحالُ إلى المالكِ أو المجلس.
> **ومصدرُ الحقائقِ:** الكودُ على `main@78723ab5` وتتبُّعُ نداءاتِ النظامِ في بيئةِ المنفِّذِ (§2)، والتشغيلةُ
> [`41181438329`](https://github.com/ovvvog/xuux/actions/runs/41181438329) (‏نتيجةُ الطفرةِ في `WL-502`).

## 1. السؤالُ

الطفرةُ `staged-mutdir` تُسقِطُ كلَّ `fsync(2)` على واصفِ مجلّدٍ في مسارِ الكاتبِ (‏`count=6` في التشغيلةِ
`41181438329`)، ومع ذلك تبقى النتيجةُ `committed` عندَ قطوعِ الدوامِ الأربعةِ (‏S3/S4 · S4/S4 · S5/S5 · ACK/ACK)،
فتسقطُ أحكامُ `PLM`. السؤالُ: **أَهوَ عمى الأداةِ، أم أنّ `fsync` المجلّدِ لا يحملُ وزناً قابلاً للرصدِ على هذا
النظامِ وهذا البروتوكول؟** الجوابُ أدناه: **الثاني** — بآليّتَين مستقلّتَين، تُغطّي كلٌّ منهما بعضَ المواضعِ.

## 2. الدليلُ: ترتيبُ النداءاتِ في معاملةٍ واحدة

قِيسَ في بيئةِ المنفِّذِ (‏Linux `6.1`، بلا device-mapper — فلا قطعَ هنا، ترتيبٌ فقط) بحائلِ `LD_PRELOAD`
يسجّلُ `fsync`/`rename`/`unlink` ونوعَ الواصفِ، على معاملةِ `crown.command` نفسِها التي يُجريها
`tests/helpers/wl-498-stage-cut-child.mjs` (‏`bootRoot` بـ`fsync: true` ومقبسِ `FileStateBoundSocket` خارجَ الجذر).
`R` = جذرُ الحالة؛ وأسطرُ الأقفالِ حُذِفَت للإيجاز:

```text
# إقلاعٌ: مزامنتا مجلّدٍ (‏2)
fsync FILE R/root-of-trust.manifest.json.tmp → rename → fsync DIR R
fsync FILE R/root-of-trust.manifest.json.tmp → rename → fsync DIR R
# S2
fsync FILE R/root-of-trust.undo.jsonl.tmp   → rename → fsync DIR R          ← (م١)
fsync FILE R/root-of-trust.manifest.json.tmp → rename → fsync DIR R         ← (م٢) ختمُ staged
===== MARK S2
# S3
fsync FILE R/commands.ledger.claims/.claiming-…
fsync FILE R/root-of-trust.undo.jsonl
unlink R/commands.ledger.claims/.claiming-… → fsync DIR R/commands.ledger.claims   ← (م٣)
fsync FILE R/root-of-trust.undo.jsonl · fsync FILE R/commands.ledger
fsync FILE R/root-of-trust.undo.jsonl · fsync FILE R/events.log
fsync FILE R/root-of-trust.undo.jsonl · fsync FILE R/events.log.head.tmp → rename R/events.log.head
===== MARK S3
# S4 — المقبسُ وحدَه، وهوَ على نظامِ ملفّاتٍ آخرَ في CI (‏WORK لا MNT)
fsync FILE SOCKET.tmp → rename SOCKET
===== MARK S4
# S5
fsync FILE R/root-of-trust.manifest.json.tmp → rename → fsync DIR R         ← (م٤) الترقية
===== MARK S5
===== MARK ACK
```

**مزامناتُ المجلّدِ: 2 في الإقلاعِ + 4 في المعاملةِ = 6** — وهوَ العددُ نفسُه الذي سجّلَه الحائلُ على العدّاءِ
(‏`MUTATION_DIR_FSYNC_SKIPPED count=6`)، فالتتبُّعُ يصفُ المسارَ المقيسَ نفسَه.

## 3. سببُ نجاحِ الاختبارِ رغمَ الطفرة

### 3.1 الآليّةُ (‏أ) — يوميّاتُ `ext4` تُثبِّتُ المعاملةَ كلَّها عندَ أيِّ `fsync` ملفٍّ لاحق

في `ext4` بـ`data=ordered` تقعُ `rename` و`unlink` وإنشاءُ المداخلِ في معاملةِ jbd2 الجاريةِ الواحدةِ لنظامِ
الملفّات. و`fsync` أيِّ ملفٍّ على النظامِ نفسِه يُجبِرُ إيداعَ تلكَ المعاملةِ — بما فيها مدخلُ المجلّدِ الذي لم
يُزامَن. فغيابُ `fsync` المجلّدِ لا يُرى عندَ قطعٍ يسبقُه `fsync` ملفٍّ لاحقٌ على `MNT`:

| الموضع | ما يليهِ قبلَ أقربِ علامة | النتيجةُ عندَ القطع |
| --- | --- | --- |
| (م١) سجلُّ التراجعِ | `fsync FILE manifest.tmp` في S2 نفسِها | مدخلُه دائمٌ رغمَ الطفرة |
| (م٢) ختمُ `staged` | **لا شيء** حتّى `MARK S2`؛ ثمّ `fsync FILE .claiming` أوّلَ S3 | غيرُ دائمٍ عندَ S2، دائمٌ عندَ S3 وما بعدها |
| (م٣) حذفُ ملفِّ المطالبة | `fsync FILE undo.jsonl` | دائمٌ رغمَ الطفرة |
| (م٤) الترقية | **لا شيء** حتّى `MARK S5`/`ACK` | **غيرُ دائمٍ** عندَ S5 وACK |

### 3.2 الآليّةُ (‏ب) — البروتوكولُ يتسامحُ مع فقدِ الموضعَين اللذَين لا تُغطّيهما اليوميّات

الموضعانِ المكشوفانِ (‏م٢ عندَ S2، وم٤ عندَ S5/ACK) **مكشوفانِ فعلاً على القرص** — لكنّ حكمَ الإقلاعِ يجعلُ فقدَهما
مكافئاً دلاليّاً للنجاة:

- **م٤ عندَ S5/ACK:** البيانُ على القرصِ يبقى `staged = {txn, from: (e, A_e)}`، والمرجعُ الخارجيُّ تقدّمَ إلى
  `e+1` في S4، والحالةُ دائمةٌ ببصمةِ `V'`. فيسلكُ الإقلاعُ القاعدةَ **B3** في
  `src/root-of-trust/production-runtime.mts` (‏«تقدّمَ المرجعُ ⇐ الحالةُ هي حالةُ المعاملةِ — تُتمُّ الترقيةُ»،
  `manifest.promoteAsync`) بعدَ أن تُطابِقَ `A'` المحسوبةُ من القرصِ المرجعَ. النتيجةُ `committed` **صحيحةٌ** هنا.
- **م٢ عندَ S2:** قبلَ أيِّ كتابةٍ للحالة؛ فقدُ `staged` يُبقي البيانَ عندَ `e` بلا ترحيلٍ والمرجعُ عندَ `e` ⇐ لا
  معاملةَ — وهوَ ما يقبلُه حكمُ `PL2` أصلاً، والحزامُ لا يطالبُ الطفرةَ بتغييره.

### 3.3 الخلاصة

**كلُّ مزامنةِ مجلّدٍ في هذا المسارِ مُغطّاةٌ إمّا بالآليّةِ (‏أ) أو (‏ب).** فالمِحكُّ `PLM` («`committed` تحتَ
الطفرةِ = عمى») **مبنيٌّ على فرضيّةٍ لا تصحُّ على `ext4`/`data=ordered` معَ هذا البروتوكول**: أن يكونَ غيابُ
`fsync` المجلّدِ قابلاً للرصدِ في نتيجةِ البروتوكول. وعندَ S5/ACK تحديداً، **مطالبةُ الطفرةِ بنتيجةٍ غيرِ
`committed` مطالبةٌ بسلوكٍ خاطئ** — لأنّ B3 مصمَّمةٌ لتُنتِجَ `committed` في هذهِ الحالِ بعينِها.

**ما لا يعنيهِ هذا:** لا يعني أنّ `fsync` المجلّدِ زائدٌ. على أنظمةٍ لا تربطُ ترتيبَ الملفّاتِ ببعضِها (‏§4.2)
قد يصبحُ ملفُّ الدفترِ دائماً قبلَ `staged` (‏م٢) — وتلكَ حالٌ يرفضُها الإقلاعُ بحسبِ بصمةِ الحالةِ (‏رفضٌ مُسمّى
لا فسادٌ صامت) **إن صحَّ التحليلُ، وهذا لم يُقَس**. الضمانُ عبرَ الأنظمةِ هوَ ما لم يُثبَت؛ لا العمى في الأداة.

**ملاحظةٌ جانبيّةٌ مقيسةٌ في التتبّع:** `rename events.log.head.tmp → events.log.head` في S3 لا تليها مزامنةُ
مجلّد (‏`persistent-log.mts`، `#writeHead`). وهذا **مقصودٌ بالتصميم**: تأخُّرُ الرأسِ بحدثٍ واحدٍ يُصلَحُ عندَ الفتحِ
(‏`repairedHead`). على `ext4` يُثبِّتُه `fsync` الملفِّ التالي؛ أمّا على نظامٍ بلا ترتيبٍ فقد يتأخّرُ أكثرَ من حدثٍ
فيُرفَضُ بـ`HEAD_MISMATCH`. **هذا حدٌّ يتعلّقُ بالتوافرِ وقابليّةِ النقلِ، لا يمسُّ صحّةَ `D3` على `ext4`،** ويُذكَرُ
ليُقيَّمَ لا ليُصلَح هنا.

## 4. تصميمُ العلاج

### 4.1 العلاجُ (‏ع١) — مِحكٌّ على مستوى نظامِ الملفّاتِ عندَ علاماتٍ دقيقةٍ بعدَ كلِّ مزامنةِ مجلّد

**الفكرة:** إن كانَ الضمانُ المطلوبُ هوَ «حينَ يعودُ `fsync` المجلّدِ يكونُ الاسمُ دائماً»، فليُقَسْ هذا بعينِه، لا
عبرَ نتيجةِ البروتوكول.

- **التصميم:** حائلٌ في وضعِ «شاهد» (‏لا يُسقِطُ شيئاً) يضعُ علامةَ `dm-log-writes` **بعدَ عودةِ كلِّ `fsync` على
  واصفِ مجلّدٍ** مباشرةً (‏`dirsync-<n>`)، ويُسجِّلُ قبلَها `(n، المسار، الاسمُ الذي أُعيدت تسميتُه)`. والحائلُ في
  العمليّةِ غيرِ المميَّزةِ لا يملكُ `dmsetup`، فيكتبُ طلبَ العلامةِ إلى FIFO **وينتظرُ الإقرار**؛ وعمليّةٌ مميَّزةٌ في
  الحزامِ تُنفِّذُ `dmsetup message … mark dirsync-<n>` ثمّ تُقِرّ — فموضعُ العلامةِ في السجلِّ متزامنٌ مع النداء.
  وفي وضعِ الطفرةِ تُوضَعُ العلامةُ نفسُها في الموضعِ نفسِه **بعدَ تخطّي** النداء.
- **المِحكُّ:** لكلِّ `n`: إعادةُ تشغيلٍ حتّى `dirsync-<n>` ⇐ تركيبٌ للقراءة ⇐ **الاسمُ الهدفُ موجودٌ ومحتواهُ
  بصمةُ الملفِّ المؤقّتِ المُزامَن**. مثبتٌ في الشاهدِ الموجب، **ومطلوبٌ سقوطُه** في الطفرةِ عندَ م٢ وم٤ على الأقلّ
  (‏حيثُ لا `fsync` ملفٍّ بينَ الإعادةِ والعلامة). أمّا م١ وم٣ فيبقيانِ أخضرَينِ تحتَ الطفرةِ **ويُعلَنانِ** مُغطَّيَين
  بالآليّةِ (‏أ) لا مقيسَين.
- **ولماذا يرى ما لا يراهُ الحزامُ الحاليُّ:** العلاماتُ الحاليّةُ عندَ حدودِ المراحلِ، وكلٌّ منها يقعُ بعدَ `fsync`
  ملفٍّ أو حيثُ يُعوِّضُ B3؛ والعلامةُ الدقيقةُ تقعُ في النافذةِ بينَ إعادةِ التسميةِ وأوّلِ `fsync` ملفٍّ تالٍ.

**الاختباراتُ التي تُثبِتُ نجاحَه:**

1. شاهدٌ موجب: كلُّ `dirsync-<n>` (‏6) ⇐ الاسمُ دائمٌ، و`e2fsck -n` نظيف.
2. طفرةٌ: `dirsync` عندَ م٢ وم٤ ⇐ الاسمُ **غيرُ** دائم (‏سقوطٌ مطلوب) — وإلّا فالمِحكُّ نفسُه أعمى.
3. طفرةٌ مضادّةٌ لأداةِ القياس: حائلٌ يضعُ العلامةَ **قبلَ** النداءِ في الشاهدِ الموجب ⇐ يجبُ أن يسقطَ (‏1)، فيثبتُ أنّ
   ترتيبَ العلامةِ معَ النداءِ مقيسٌ لا مفترض.
4. اختباراتُ وحدةٍ بلا نواةٍ لدالّةِ الحكمِ الجديدة (‏على نمطِ `live-39-judge.sh` في `WL-499`).

**المخاطرُ والآثارُ الجانبيّة:** (‏أ) ثمنُ زمنٍ: ستُّ إعاداتٍ إضافيّةٍ لكلِّ وضعٍ على عدّاءٍ طويلٍ أصلاً؛ (‏ب) تزامنُ
FIFO يضيفُ تأخيراً يغيّرُ التوقيتَ لا الترتيب — والمِحكُّ ترتيبيٌّ، لكن يُعلَنُ؛ (‏ج) هوَ قياسٌ لـ«الاسمِ دائمٌ عندَ
عودةِ النداء» لا لـ`D3` البروتوكوليِّ — **فلا يُقدَّمُ إغلاقاً لـ`LIVE-39`** بل دليلاً على أنّ مزامنةَ المجلّدِ تعملُ
وتُرى؛ (‏د) يمسُّ `scripts/` و`tests/` ⇐ دورةُ `R7` (‏`OPS-1/R7-COST`).

### 4.2 العلاجُ (‏ع٢) — نظامُ ملفّاتٍ لا تُغطّي يوميّاتُه الغياب

- **التصميم:** سيناريوهاتُ الطفرةِ والشاهدِ نفسُها على `mkfs.ext4 -O ^has_journal` (‏ext4 بلا يوميّات)، وبديلاً على
  XFS وbtrfs بقيدٍ مُعلَنٍ لكلٍّ. **فرضيّةٌ تُقاس لا تُفترض:** بلا يوميّاتٍ يزولُ (‏أ)، فيظهرُ غيابُ م٢ عندَ S3
  (‏الدفترُ دائمٌ و`staged` غيرُ دائم ⇐ رفضُ إقلاعٍ مُسمّى بدلَ `committed`). أمّا XFS فقد يُغطّي بإيداعِ السجلِّ
  المرتَّبِ كما في `ext4`، وbtrfs بسجلِّ شجرةٍ لكلِّ عقدةٍ — **سلوكُهما يُقاسُ ولا يُتنبَّأُ به هنا.**
- **الاختبارات:** شاهدٌ موجبٌ أخضرُ على كلِّ نظامٍ (‏وإلّا فالكودُ نفسُه غيرُ دائمٍ عليه — نتيجةٌ أهمّ)، وطفرةٌ تُنتِجُ عندَ
  S3 حكماً غيرَ `committed`. ويُعدَّلُ المِحكُّ: **عندَ S5/ACK `committed` هوَ الصحيحُ تحتَ الطفرةِ أيضاً (‏B3)**،
  فلا يُطالَبُ بالسقوطِ هناك.
- **المخاطر:** (‏أ) ext4 بلا يوميّاتٍ يتركُ نظاماً يحتاجُ `e2fsck -p` بعدَ القطع ⇐ حكمُ `PL4` (‏`e2fsck -n` نظيف) لا
  ينطبقُ كما هوَ ويلزمُه نصٌّ مختلف؛ (‏ب) قد يكشفُ أنّ الشاهدَ الموجبَ نفسَه يسقطُ على نظامٍ ما — وهوَ دليلٌ على
  ضمانٍ ناقصٍ عبرَ الأنظمة، فيصيرُ قرارَ نطاقٍ لا خللَ اختبار؛ (‏ج) لا يُدَّعى أنّ نظامَ الإنتاجِ أحدُها — **نظامُ ملفّاتِ
  الإنتاجِ غيرُ مُعلَنٍ في المستودع.**

### 4.3 العلاجُ (‏ع٣) — تصحيحُ المِحكِّ `PLM` نفسِه (‏لا علاجَ للكود)

حكمُ `PLM` الحاليُّ يطالبُ بنتيجةٍ غيرِ `committed` عندَ S5/ACK تحتَ الطفرة، والبروتوكولُ يُنتِجُ `committed` صحيحاً
هناك (‏§3.2). **فالمِحكُّ يُعادُ تعريفُه** إلى ما يملكُ البروتوكولُ أن يُغيِّرَه: عندَ S5/ACK `committed` مقبولٌ ويُرفَقُ
بدليلِ مسلكِ B3 (‏البيانُ على القرصِ `staged` قبلَ الإقلاع)؛ ويُطالَبُ بالرصدِ في (‏ع١) و(‏ع٢) وحدَهما. **وهذا تغييرٌ
في معنى ما يُدَّعى مقيساً** ⇐ يُقدَّمُ للجهةِ المخوَّلةِ ولا يُدمَجُ قبلَ حكمِها.

## 6. قراراتٌ مطلوبةٌ من الجهةِ المخوَّلة

1. **أَيُقبَلُ التفسيرُ في §3** — أنّ العمى خاصيّةُ `ext4`/`data=ordered` معَ B3، لا خللُ أداة؟
2. **أيُّ نظامِ ملفّاتٍ يَعِدُ به المشروعُ لـ`D3`؟** `ext4`/`data=ordered` وحدَه (‏فيكفي تصحيحُ `PLM` وتوثيقُ القيد)،
   أم ضمانٌ قابلٌ للنقلِ (‏فيلزمُ (‏ع٢) شرطاً للإغلاق)؟
3. **أَيُعادُ تعريفُ `PLM`** وفقَ (‏ع٣)؟
4. **أَيُؤذَنُ بتنفيذِ (‏ع١)** سيناريو اختياريّاً، معَ قبولِ دورةِ `R7` التي يُطلقُها دمجُه؟

## 7. إعادةُ إنتاجِ التتبّع (‏§2)

```c
// tr.c — gcc -shared -fPIC -o tr.so tr.c -ldl ; LD_PRELOAD=./tr.so node child.mjs transact <dir>
#define _GNU_SOURCE
#include <dlfcn.h>
#include <fcntl.h>
#include <stdio.h>
#include <sys/stat.h>
#include <unistd.h>
static void path(int fd, char *b, size_t n) {
  char p[64]; snprintf(p, 64, "/proc/self/fd/%d", fd);
  ssize_t r = readlink(p, b, n - 1); b[r < 0 ? 0 : r] = 0;
}
int fsync(int fd) {
  static int (*f)(int); if (!f) f = dlsym(RTLD_NEXT, "fsync");
  struct stat st; char b[512]; path(fd, b, 512);
  int d = fstat(fd, &st) == 0 && S_ISDIR(st.st_mode);
  fprintf(stderr, "TRACE fsync %s %s\n", d ? "DIR " : "FILE", b); return f(fd);
}
int rename(const char *a, const char *c) {
  static int (*f)(const char *, const char *); if (!f) f = dlsym(RTLD_NEXT, "rename");
  fprintf(stderr, "TRACE rename %s -> %s\n", a, c); return f(a, c);
}
```
